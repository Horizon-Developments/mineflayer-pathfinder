<topic name="project-identity">
This is a mineflayer-pathfinder-style bot pathfinding plugin for Minecraft (Node.js, uses `vec3`, `prismarine-nbt`, a `bot.registry` for block/item data by version). Core loop: astar.js (generic search) <- movements.js (Move-generation / cost / feasibility rules, the "physics knowledge") <- Move.js (node shape) <- goals.js (termination/heuristic). boat.js is a separate real-time physics controller invoked once a boat move is chosen. hostiles.js augments cost fields for mob avoidance. human.js/movelog.js are execution/diagnostics layers, not the search.
</topic>

Step 5 (cluster #4 slice: swimming) findings:
- Before this step, liquid handling was entirely horizontal-and-one-directional: getMoveForward/getMoveDiagonal already generated in-water horizontal moves (adding liquidCost, never refusing a liquid destination outright) but getMoveUp explicitly refused any liquid cell (`if (block1.liquid) return`), and getMoveDown/getMoveDropDown's liquid awareness only ever went one way (falling/dropping INTO water from above via getLandingBlock). There was no way to swim straight up or down through a water column at all. New getMoveSwimUp/getMoveSwimDown close that gap: both require the current cell AND the neighbour cell (above/below) to already be liquid, and deliberately stop one cell short of a non-liquid neighbour - reaching the surface and climbing out, or reaching a floor and standing on it, stays the job of the existing forward/diagonal/down/drop-down generators, not these two. Gated behind allowSwimming (new, default true - basic/common/not risky, per the allowParkour/allowSprinting convention).
- Confirmed no new Move-hash flag was needed for this (the open question step 4's CONTEXT.md next_step raised): unlike a boat, which can occupy the *same* (x,y,z) as either "standing on shore" or "floating on water" (two different entity states at identical coordinates, hence needing the `boat` hash flag), a liquid cell is always a liquid cell - there is no second, non-swimming way to legitimately occupy a fully-submerged (x,y,z). So "in water" is fully determined by getBlock(node,0,0,0).liquid, not by anything that needs its own search-state flag.
- Bubble columns: classified (bubbleColumnBlocks) and now DIRECTION-AWARE (corrected post-step-5, still within step 5's slice, per direct user feedback - not a step-6 item): bubble_column blocks carry a boolean `drag` block-state property (drag:false = pushes up, drag:true = drags down), readable via block.getProperties() (prismarine-block), the same block-state-read mechanism this file previously assumed it didn't have available anywhere (see movements.js-current-state - that assumption was wrong for this specific block). getBlock() now sets b.bubbleDrag (false/true/undefined) whenever b.type is a bubble column and the property is readable; undefined means either not a bubble column or the running version's block objects don't expose getProperties(), in which case it gracefully falls back to flat swim cost. getMoveSwimUp discounts (bubbleColumnCostMultiplier=0.6) when bubbleDrag===false (column pushes up, helping the move) and penalizes (new bubbleColumnOpposingCostMultiplier=1.7) when bubbleDrag===true (column drags down, fighting the move); getMoveSwimDown is the mirror image. This supersedes the original step-5 "direction-agnostic, can't tell up from down without a deeper block-state read" note - the deeper read turned out to be a single getProperties() call, not the source-block-at-column-bottom lookup originally assumed necessary.
- Explicitly deferred, not attempted: water currents (flowing-water push) and Dolphin's Grace (a status-effect speed buff) are both execution-layer/real-time-physics concerns, the same category as sprinting/momentum from cluster #1 - a discrete A* cell graph has no natural place for "being pushed sideways while crossing a cell" or "a timed buff changing speed," any more than it did for sprint-jump timing. Sprint swimming likewise deferred for the same reason. Waterlogged-block movement was looked at and set aside like the bed-landing case in step 3: knowing whether a given fence/slab/stair is waterlogged needs a block-state/metadata read (a boolean property on the block, not something inferable from block id/type alone), which this file doesn't do anywhere else - flagged rather than guessed at. Boat-travel extensions (accel/steer/turn/brake/launch/retrieve/shortcuts, land<->boat transitions beyond the existing embark/cruise/disembark) were also deferred this step, per step 4's own suggestion to split cluster #4 - getMoveBoatEmbark/Cruise/Disembark and boat.js's physics layer already exist and are the right place to extend, but doing that carefully deserves its own step rather than being squeezed in alongside swimming.
- Swimming through 1-block gaps: not specially handled, and worth flagging as a known imprecision rather than assumed solved - getMoveForward/getMoveDiagonal still require a 2-tall clear space (blockB above the destination must be `.safe`) the same as walking, whereas a swimming player's actual hitbox/clearance needs are different underwater. Left as-is (the existing check is conservative, not broken - it just may reject some gaps a real swimming player could fit through).

Step 6 (cluster #5/#6 slice, FINAL step) findings:
- getMoveUp already had two branches: `block1.climbable` (current cell is a ladder/vine/scaffolding - just move up, no placement, cost 1) and the else branch (place a block below and jump, gated by allow1by1towers). The first branch is climbing UP and has worked since step 3 added vines/scaffolding to climbables; the second branch IS pillaring/towering and needed no new work at all. Both were confirmed by reading, not assumed - neither needed code changes this step.
- The real gap was descent: getMoveDown/getLandingBlock's while-loop treats any `.safe` cell (which includes climbable, per getBlock's `b.safe = boundingBox==='empty' || b.climbable || carpets.has(type)`) as pass-through air on the way down to solid ground, then prices the ENTIRE resulting distance through getFallDamageCost - i.e. a ladder bolted all the way to bedrock got priced identically to jumping off the top with nothing to hold onto. New getMoveClimbDown checks only `getBlock(node,0,-1,0).climbable` and, if true, emits a single one-cell-down Move at flat cost `this.climbCost` (=1, new). Because this is cheaper per-cell than a multi-block fall-damage move to the same eventual floor, A* will chain it down a real ladder/vine/scaffolding column instead of taking the fall-priced alternative, whenever one exists.
- Side effect treated as intentional, not accidental: because getMoveClimbDown only ever resolves ONE cell (unlike getLandingBlock, which searches all the way to the ground), a bot already mid-fall that reaches a climbable cell will have that cell offered as a neighbour of its current (mid-air-equivalent, i.e. last stable) node like any other, letting the search route through it and effectively cap the fall there instead of continuing to the true floor - this is the "grab a ladder/vine/scaffolding to stop a fall" behavior cluster #6 asks for, obtained for free rather than built as a separate MLG-specific move. Not verified against a running bot (same missing-dependencies blocker as everything else) - this is a claim about what the cost graph SHOULD produce, not an observed result.
- Deliberately not modeled: scaffolding's sneak-to-fall-through shortcut (an alternate, faster descent that skips the climb-down entirely) - getMoveClimbDown treats all climbables uniformly and has no sneak/fall-through concept, same category of omission as scaffolding's other unmodeled behaviors noted back in step 3.
Also learned: pre-step-2, getMoveDropDown/getMoveDown/getLandingBlock treated any drop up to maxDropDown (default 4 blocks) as a flat cost of 1 — identical to a single walk step — with zero fall-damage modelling, and anything past maxDropDown was simply infeasible (hard cutoff, not a cost tradeoff). Step 3 extended getFallDamageCost to a 2-arg form: getFallDamageCost(distance, landingBlock). landingBlock is optional (old 1-arg call sites elsewhere would still work, though there are none outside movements.js). If landingBlock.type is in this.fallDamageNegatingBlocks (slime_block/honey_block/powder_snow) the cost is 0 regardless of distance; if it's in this.fallDamageReducingBlocks (a Map, currently just hay_block/hay_bale -> 0.2) the per-block-beyond-safe cost is multiplied by that factor. - New block-name based classification: build Sets in the Movements constructor from `bot.registry.blocksByName`/`itemsArray`, guarding optional blocks with `if (registry.blocksByName.x)` (see existing cobweb/web guard) since block existence varies by MC version.
